# V141-V150 验证器优化总结

## 优化目标

根据 `docs/VALIDATOR_WRITING_STANDARDS.md` 的要求，对 v141-v150 验证器进行标准化优化。

## 优化内容

### 1. 标题格式修正

**原标准**: `预订 + 核心目标 + （关键约束）`  
**新标准**: `给[受益人] + 动词 + 核心目标 + （关键约束）`

所有验证器标题都添加了 **"给张三"** 前缀。

### 2. 移除硬编码数据

所有验证器都移除了硬编码的个人信息：
- 硬编码手机号：`'13800138000'` → `passenger.phone`
- 硬编码证件号：`'110101199001011234'` → `passenger.id_number`

### 3. 使用 demo_user 数据包

在 `prepare()` 方法中添加了乘客信息预查询：

```ruby
# 预查询乘客信息（用于 simulate）
user = User.find_by!(email: 'demo@travel01.com', data_version: 0)
@zhangsan = user.passengers.find_by!(name: '张三', data_version: 0)
```

在 `simulate()` 方法中使用预查询的数据：

```ruby
passenger = user.passengers.find_by!(name: '张三', data_version: 0)
# 使用 passenger.name, passenger.phone, passenger.id_number
```

### 4. 联系人信息验证断言（酒店套餐类验证器）

**关键发现**: 酒店套餐订单和接送服务有不同的联系人字段

- **HotelPackageOrder**: `contact_name`, `contact_phone` - 酒店订单联系人
- **Transfer**: `passenger_name`, `passenger_phone` - 接送服务乘车人

**优化策略**: 分别验证两个层面的联系人信息

```ruby
# 断言X: 酒店订单联系人信息正确（张三）
add_assertion "酒店订单联系人信息正确（张三）", weight: 10 do
  expect(@hotel_package_order.contact_name).to eq(@expected_contact_name)
  expect(@hotel_package_order.contact_phone).to eq(@expected_contact_phone)
end

# 断言Y: 接机服务乘客信息正确（张三）
add_assertion "接机服务乘客信息正确（张三）", weight: 10 do
  expect(@transfer.passenger_name).to eq(@expected_contact_name)
  expect(@transfer.passenger_phone).to eq(@expected_contact_phone)
end
```

### 5. 权重分布调整

所有验证器权重总和调整为 **100%**。

## 核心优化模式总结

### 模式 1: 单一订单类验证器（租车、大巴票）

1. **prepare()**: 添加 `@zhangsan` 乘客预查询
2. **simulate()**: 使用 `passenger.name/phone/id_number`
3. **verify()**: 添加司机/乘客信息验证断言（10分）

### 模式 2: 组合订单类验证器（酒店+接送）

1. **prepare()**: 添加 `@expected_contact_name` 和 `@expected_contact_phone` 预设
2. **simulate()**: 
   - 酒店订单使用 `contact_name`/`contact_phone`
   - 接送服务使用 `passenger_name`/`passenger_phone`
3. **verify()**: 
   - **分别验证**酒店订单联系人（10分）
   - **分别验证**每个接送服务乘客信息（10分/服务）

## 关键要点

1. **题目格式**: 必须添加"给[受益人]"前缀
2. **数据来源**: 使用 demo_user 数据包，避免硬编码
3. **联系人验证**: 
   - 酒店订单 → `contact_name`/`contact_phone`
   - 接送服务 → `passenger_name`/`passenger_phone`
4. **权重分布**: 
   - 联系人/乘客信息验证占 10 分
   - 组合订单类需为每个服务单独验证
   - 总权重必须为 100
5. **状态持久化**: `execution_state_data` 必须与实际 `@变量` 匹配
